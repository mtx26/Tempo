# Architecture decisions

- D001: Home Assistant is the ONLY user-facing interface; custom HACS-compatible integration. No independent frontend.
- D002: Python/FastAPI + PostgreSQL + worker + OR-Tools CP-SAT are baseline candidates; benchmark before locking production.
- D003: MOTIS is preferred routing candidate; benchmark against OpenTripPlanner with Belgian multi-operator and realtime data.
- D004: Belgian Mobility Open Data replaces TEC-only feed assumptions. Verify actual coverage, access terms and STIB realtime adapter.
- D005: Actual location always from configured HA phone tracker; future route origin derives from planned sequence where applicable.
- D006: University iCal timetable fixed; personal study blocks movable. Study target dates soft by default, hard only if explicitly stated.
- D007: All training movable; races/competitions fixed.
- D008: Protected changes require approval; ordinary flexible planning can change automatically.
- D009: No destructive/server deployment without user approval; keep secrets out of repository.
- D010 (DECIDED 2026-11-23 by user): two repositories — private Tempo Core (this repo: backend, worker, DB, routing, deployment) and a public-ready `tempo-homeassistant` repo (local sibling directory `../tempo-homeassistant`, `custom_components/tempo/` at its root). Neither is published without explicit approval. Original analysis: HACS requires `custom_components/<domain>/` at the root of a **public** GitHub repo with one integration. Current `homeassistant/custom_components/tempo/` is not HACS-installable as-is. Options: dedicated public integration repo (recommended; backend stays private) or move `custom_components/` to this repo's root and make it public. See docs/FEASIBILITY.md §5.
- D011: Backend toolchain = Python 3.13 managed by `uv` (lockfile `backend/uv.lock`), ruff (lint+format), mypy `--strict`, pytest + pytest-cov. `tzdata` is an explicit dependency so IANA zones work identically on Windows dev machines and Debian containers.
- D012: iCal expansion uses `icalendar` + `recurring-ical-events`, guarded by a raw-source pre-scan because the library (a) adds RECURRENCE-ID to non-recurring events and (b) silently swaps inverted DTSTART/DTEND. Occurrence identity = (UID, RECURRENCE-ID in UTC, only for recurring UIDs). All-day events are reported as skipped, not as blocking commitments. Hardened after adversarial review: invalid data is tracked per occurrence (an invalid override no longer drops the whole series), unknown TZIDs are rejected instead of reinterpreted, duplicate non-recurring UIDs are all kept with a warning, and `diff_events(window=...)` restricts comparison to the intersection of sync windows. Known limitations: moving a series' master DTSTART (or turning a single event into a series) yields removed+added instead of changed — the future proposal layer must pair them by UID + local date; floating times inside a DST gap/overlap are not flagged.
- D013: MVP routing uses Belgian GTFS static for all four operators + GTFS-RT for SNCB/TEC/De Lijn in MOTIS (`/api/v6/plan`, `arriveBy`). STIB has no GTFS-RT/SIRI: STIB legs are labelled "static timetable only" until a dedicated adapter is validated. Live polling requires a user-created free Belgian Mobility Standard account (anonymous quota 100 req/day is insufficient).
- D014: Service token hardening: `hide_input_in_errors`, no whitespace, ≥16 distinct chars (generate with `secrets.token_urlsafe(32)`), OpenAPI/docs disabled, token readable from Docker secret `/run/secrets/tempo_api_token` (preferred over env vars in Swarm).
- D015: Milestone order adjusted: scheduler (M3) before persistence, because the schema depends on scheduler entities (blocks, locks, schedule versions). Scheduler = CP-SAT with an independent deterministic validator (`validate_plan`); a plan with violations is never proposed.
- D016: Local PostgreSQL integration tests use `pgserver` (PostgreSQL 16 binaries, run under Python 3.12 via `scripts/dev_postgres.py`) because Docker is unavailable on the dev PC; production target remains the PostgreSQL container on Swarm (version to align before deployment).
- D017: iCal persistence safety: soft-delete with history; no deletion for UIDs invalid in the current feed; empty feed or removals > 50 % (and >= 3) of the stored window ⇒ sync marked `suspect`, removals withheld; per-source `pg_advisory_xact_lock`; audit lists occurrence keys and changed field names only (no titles/locations). Callers parse window + margin (tests: 60 days). Requires PostgreSQL >= 15 (`NULLS NOT DISTINCT`).
- D018: Alembic upgrades are serialised by `pg_advisory_xact_lock` in `env.py` (proved: without it 2 of 3 concurrent processes fail). Schema downgrade helper is test-only.
